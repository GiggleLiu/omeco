## Lessons we learnt

- **Observation**: five mechanically different searches (011 subtree-shift,
  012 projection, 015 population, 017 λ-ramp, 018 memetic) all landed
  within 0.35 log2 of each other on both targets (reg3 39.95–40.29, syc
  61.51–62.10), collectively ~4.3/~9.7 below the TreeSA references.
  **Root cause**: the gain does not come from any specific move set — it
  comes from the shared objective change (treat sc-cap as the operative
  constraint, `sc_target = cap` instead of omeco's default 20) plus
  full-budget anytime annealing with any basin-escape mechanism. The
  default `sc_target=20` actively sabotages TreeSA on instances whose
  feasible optimum sits at sc 33–53: it drags the search toward
  low-memory/high-flop trees. **Evidence**: 018's ablation (soft penalty
  at cap moved reg3 56.8→40.0, its novel DP component gained 0.002); the
  0.35-wide cluster across five independent implementations; references
  measured with default sc_target. *Confirmed.* **Implication**: the
  publishable object is "sc-budget-aware annealing" as a principle, not a
  named move set; and omeco's TreeSA default `sc_target` is a footgun
  worth fixing in the library.
- **Observation**: 014 (LNS) and 016 (tabu) scored 4–5 log2 worse than
  their own unscored smoke tests; 011/015/017/018's smoke numbers
  replicated to within 0.1. **Root cause**: 014/016 have heavy-tailed
  run-to-run variance (016's own five-run spread included 45.1; 014's
  TreeSA-warmup + LNS split is sensitive to the warmup's stochastic
  outcome), and a single scored run samples that tail; the SA-family
  methods are intrinsically lower-variance. **Evidence**: 016's LOG
  documents the 1-in-5 tail; 014's LOG shows smoke 40.3 vs scored 45.0.
  *Confirmed for 016, suspected for 014* (would confirm with repeated
  scoring, not spent this cycle). **Implication**: variance is now a
  first-class quality axis — record-chasing favors low-variance
  mechanisms; high-variance ones need internal restarts-and-min to be
  competitive per single run.
- **Observation**: 013 (simplification) gained nothing despite sycamore
  carrying 106 rank-1 tensors. **Root cause**: TreeSA spends negligible
  budget on trivially-decidable boundary contractions anyway — search-space
  size was not the binding constraint; the sc objective was.
  **Evidence**: 013 held the optimizer at baseline and scored at reference
  level on both targets. *Confirmed.* **Implication**: blacklist
  "search-space reduction" as a standalone lever on these targets;
  simplification remains harmless plumbing, not a win.

Ranked most-important finding: the `sc_target = cap` objective principle
(it explains ~all of the 4.3/9.7 improvement); second: variance as a
selection criterion between otherwise-equivalent mechanisms.

### Literature check

`sc_target = cap` as the operative annealing objective matches the
memory-bounded practice in [kalachev_2021_multi] (β-penalty on
log2(M/Mmax) overflow) — our finding sharpens it: on instances whose
optimum sits near the cap, target-the-cap dominates target-a-low-sc. The
five-way basin convergence at matched budget echoes the plateau behavior
described in [gray_2020_hyper]'s anytime curves. No paper in `.knowledge/`
reports the specific failure mode "default sc_target sabotages TreeSA on
high-sc-optimum instances" — novel at the library/engineering level; the
record-sized quality gains need a cotengra head-to-head before any
external claim. Shelved insights: none (all Selected).
